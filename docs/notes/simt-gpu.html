1 · A GPU is not a bunch of CPUs

It's a natural first guess: "a GPU is lots of little CPUs". If it were, each thread would have its own fetch unit, decoder, branch predictor and control logic, and 64 threads would cost 64 front ends. That front end is most of what a CPU is. A GPU core makes the opposite bet. It keeps one front end and spends the area on many datapaths, which all execute the same instruction on different data. This is called SIMT: single instruction, multiple threads.

The riscv-core blocks went in unchanged. The decoder and ALU don't care whether one thread or eight are behind them. What's new is everything around them: the scheduler, the masks, the per-thread state, and the memory path.

The catch, and the rest of this page: sharing one instruction stream only pays when the 8 threads want the same instruction (section 5) and their memory accesses sit next to each other (section 6). GPUs are fast on code like that and slow on code that isn't.

2 · Grid, block, warp, thread

A kernel is one program that every thread runs. You launch it over a grid of blocks. Each block has up to 32 threads and runs on one core. The core splits the block into warps of 8. The warp is what the hardware schedules: 8 threads, 1 instruction at a time.

__global__ void vecadd(int *a, int *b,
                       int *c, int n) {
  int i = blockIdx.x * blockDim.x
        + threadIdx.x;
  if (i < n) c[i] = a[i] + b[i];
}

The dispatcher in gpu_top.sv hands out blocks: whenever a core goes idle, it gets the next block number. With 32 blocks and 2 cores, each core runs about 16 blocks one after another. Threads exit with ecall, and when every thread of a block has exited, the core asks for another.

3 · The pipeline, and why it has no forwarding

Three stages: F picks a warp (round robin among warps that are ready), works out its PC and active mask, and reads instruction memory. D decodes and reads the 8 lanes' registers. X runs 8 ALUs, writes back, and moves each active thread's PC on.

Remember riscv-core: forwarding paths, a load-use stall, and flushes on taken branches, all because one program had several of its instructions in the pipeline at once. Here, a warp never has more than one instruction in flight. A warp is marked busy when it's picked and freed when its instruction finishes. So an instruction can never need the result of an earlier one that isn't done yet: no data hazards, no forwarding, no branch prediction, no flushes. The pipeline is still full, because the next instruction in it comes from a different warp.

cycle123456
Fw0w1w2w3w0w1
Dw0w1w2w3w0

With 4 ready warps the core issues every cycle. w0's second instruction enters F in cycle 5, after its first has written back in cycle 3, so even a branch has resolved in time.

The cost: a block with only one warp can issue only every few cycles, and stalls completely on memory. That's the next section.

4 · Hiding latency with other warps

A CPU fights memory latency with caches, and riscv-core's memory answered in one cycle anyway. This GPU's memory takes 8 cycles, plus queueing. When a warp issues a load, it goes to the LSU and the warp sleeps until the data is back. The scheduler simply skips it and runs other warps.

test_warps_hide_latency runs the same 512 vecadd threads two ways:

LaunchWarps per coreCycles
64 blocks of 8 threads14,002
16 blocks of 32 threads41,146

Same work, 3.5× faster with 4 warps. This is why real GPUs keep dozens of warps resident per SM: an H100 SM can hold 64. The register file has to hold all of them at once, which is why GPUs have huge register files (256 KB per SM on recent NVIDIA parts) and comparatively small caches.

5 · Divergence: when threads in a warp disagree

All 8 lanes share one fetch. So what happens at if (x is odd) when lanes 1, 3, 5, 7 are odd and the rest are even? The warp can't go both ways at once, so it goes both ways one after the other. It switches off the lanes that don't belong on the current side. The bitmask of switched-on lanes is the active mask.

Our rule (min-PC): every thread keeps its own PC. The scheduler runs the warp at the smallest PC among its live threads, with exactly the threads at that PC switched on. Trace it for one warp:

0x00  andi  t1, a1, 1        # odd?
0x04  beqz  t1, even
0x08  addi  a2, a2, 10       # odd side
0x0c  j     done
0x10  even: addi a2, a2, 20  # even side
0x14  done: sw a2, 0(a3)

Lanes 1, 3, 5, 7 hold odd values. After the beqz, the odd lanes are at 0x08 (not taken) and the even lanes are at 0x10 (taken). 0x08 is smaller, so the odd side runs first, then jumps to 0x14 and waits there. Now 0x10 is the smallest, so the even side runs. Then everyone is at 0x14, and the warp is back to full width, without anyone telling it where the if/else ends.

● = lane active. A shaded cell shows the PC where that lane is waiting.

SIMD efficiency = useful lane-slots ÷ total lane-slots = (8+8+4+4+4+8) ÷ (6×8) = 36/48 = 75%. The GPU counts this in hardware (thread_instrs ÷ (warp_instrs × 8)).

Loops work the same way. Threads that still have iterations to go sit at lower PCs (inside the loop), so they keep running. Threads that are done wait at the exit. The warp leaves the loop only when its slowest thread does. That’s what costs Collatz: the benchmark in section 7 measures 40% SIMD efficiency, so more than half the lanes sit idle at any moment.

The one thing min-PC can't do. Say lane 0 spins in a loop waiting for lane 1 (same warp) to set a flag, and lane 1's store is later in the program. Lane 0's PC is always the smaller one, so the warp only ever runs lane 0, lane 1 never gets to the store, and the warp deadlocks. Pre-2017 NVIDIA GPUs had the same problem with their reconvergence stack. Volta added independent thread scheduling so the hardware can occasionally run the other path. Our GPU keeps the simple rule. Fine-grained locking between threads of one warp just isn't allowed.

6 · Coalescing: why access patterns matter

Memory is read and written in 32-byte lines (8 words, one per lane). When a warp executes lw, the LSU looks at all 8 addresses, takes the first pending lane's line, serves every lane whose address falls in that same line with one request, and repeats until all lanes are served. Each request takes one memory slot, shared by both cores.

test_coalescing reads in[i*stride] with 256 threads (32 warps) and checks the exact number of lines sent. Per warp: 4 argument loads (all lanes read the same word → 1 line each), the gather, and 1 line for the store.

The RTL produced exactly these numbers. At stride 8 every lane needs its own line, and the gather costs 8× the memory traffic of stride 1 for the same amount of useful data. On a real GPU this is the first thing to fix in a slow kernel. NVIDIA's memory system also works in 32-byte sectors, so the rule of thumb carries over directly. Matmul shows both cases in one loop: A[row][k] is the same word for every lane (1 line, a broadcast), and B[k][col] is consecutive across lanes (1 line, coalesced).

7 · CPU vs GPU, measured

tb/test_bench.py runs the same algorithm on the same data, on riscv-core's 5-stage pipeline (in lockstep with its golden model) and on the GPU, and checks both results. The CPU's memory answers in 1 cycle. For fairness the GPU runs twice: with 2-cycle memory (the fastest our memory model allows), and with the default 8.

workloadCPU cyclesGPU, 2-cycle memGPU, 8-cycle memGPU SIMD efficiency
vecadd (1024)11,2761,698 (6.6×)2,290 (4.9×)100%
Collatz (256)169,99819,169 (8.9×)19,287 (8.8×)40%

Reading the table

  • Peak. 2 cores × 8 lanes = 16 thread-instructions per cycle. The CPU's peak is 1, and it actually reaches 0.82 instructions per cycle on vecadd and 0.64 on Collatz, because every taken branch flushes two instructions (the 2-cycle penalty from Days 1–2). So speedups above 16× are possible against this CPU.
  • vecadd is memory-bound. Every lane is useful (100% SIMD efficiency), but each GPU thread runs 20 instructions (ID math, four argument loads, the bounds check, then the add), while the CPU loop needs 9 per element. That's more than 2× the work before we start. The GPU sustains 12.1 thread-instructions per cycle with 2-cycle memory and 8.9 with 8-cycle memory: 7 of every 20 instructions are loads or stores, and a warp sleeps through each one.
  • Collatz is compute-bound and divergent. The cores issue an instruction on 91% of cycles, so there's plenty to do, but only 40% of the lanes in each issue are useful, so the GPU gets 5.8 useful thread-instructions per cycle. With full warps at the same issue rate it would be about 23× faster than the CPU instead of about 9×. Divergence cost it about 2.5×. Memory latency barely shows up: 160 memory lines in about 19,000 cycles.
The lesson isn't "GPU fast, CPU slow". The GPU needs thousands of independent threads to win. Give it one thread and it loses badly. A lone warp can issue only every third cycle (its next instruction waits for the previous one to write back), it uses 1 of 8 lanes, and it sleeps through every memory access. riscv-core runs that same thread at nearly one instruction per cycle. Throughput machine vs latency machine: that's why every real system has both.

8 · How we know it's right

  • Golden model. Every kernel also runs on riscv-core's Python ISS, one thread at a time (a subclass adds mul and the ID registers). Final memory must match byte for byte, and the GPU's thread_instrs counter must equal the model's instruction count. A lane that runs when it shouldn't changes that count even if memory looks fine.
  • Plain-Python check. Each directed test also compares against a one-line Python answer, so a bug shared by the kernel and the model can't hide.
  • Random kernels (randkernel.py): nested data-dependent if/else, loops of 1–4 trips per thread, calls, early exits, uncoalesced gathers, byte/halfword stores, random grid and block sizes.
  • Mutation testing (mutate.py): 10 realistic bugs planted one at a time, for example "no divergence mask", "ECALL kills the whole warp", "SH writes only its low byte", "dispatcher launches one block too many". Result: 10/10 caught. The first run said 9/10: "x0 becomes writable" survived. That wasn't a gap in the tests. The read port returns 0 for x0 no matter what the register file holds, so a write to x0 can never be seen. A bug nobody can observe is an equivalent mutant, and it has to be replaced, not "fixed". The replacement (x0 read from the register file) is caught immediately.

10 · Gate quiz

Answer each out loud or on paper before opening it. Passing the gate means getting 7 of 8 without peeking.

1. In one sentence, what is shared and what is per-thread in a SIMT core?

Shared: fetch, decode, scheduling and branch control (one instruction stream per warp). Per thread: registers, PC and an ALU lane. So 8 threads cost 8 datapaths but only one front end.

2. Why does our core need no forwarding and no load-use stall?

A warp has at most one instruction in flight; its next instruction can't be fetched until the previous one has written back. The pipeline stays full with instructions from other warps, which are independent by construction.

3. A warp of 8 hits an if/else: 3 lanes take the "then" side (4 instructions, including its jump), 5 take the "else" side (6 instructions). What's the SIMD efficiency of just that region?

Issues: 4 + 6 = 10. Useful lane-slots: 4×3 + 6×5 = 42. Efficiency = 42 / (10×8) = 52.5%.

4. With stride 2 (thread i reads word 2i), how many 32-byte lines does one warp's load need, and why?

The 8 lanes span 8 × 8 = 64 bytes = 2 lines, so 2 requests. Stride 1 would be 1 line, stride 8 would be 8.

5. Why did the same 512 threads run 3.5× slower as 64 one-warp blocks than as 16 four-warp blocks?

With one warp per core, every load leaves the core with nothing to issue for the whole memory latency. With four, the scheduler fills those cycles with the other warps. Latency is hidden by parallelism, not removed.

6. Explain why the min-PC rule makes an if/else reconverge without any hint about where it ends.

Code after the if/else sits at a higher address than both sides. Whichever side is at the lower PC runs until it reaches the join point. Then the other side is the lowest and runs. Once both reach the join, all threads share one PC and the mask is full again.

7. Give a program that deadlocks on our GPU but would work on 8 separate CPUs.

Two threads of the same warp: thread 0 spins while (flag == 0); and thread 1 later does flag = 1 at a higher PC. Min-PC always picks thread 0's loop, so thread 1 never runs. On separate CPUs both make progress. (Volta's independent thread scheduling exists to fix this.)

8. Collatz has only 40% SIMD efficiency, yet the GPU beats the CPU by more on Collatz (8.8×) than on vecadd (4.9×). Why?

vecadd is memory-bound and the GPU does more than 2× the CPU's instructions per element (per-thread ID math and argument loads), and warps sleep on every load. Collatz is a long compute loop: the cores issue almost every cycle and memory hardly matters, and the CPU itself runs at only 0.64 instructions per cycle because of taken-branch flushes. Divergence still throws away about 60% of the lanes (about 23× would be possible with full warps).
