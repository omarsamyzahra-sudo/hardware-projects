The RV32I core, cycle by cycle

Every table below was recorded from the real RTL (riscv-core, Icarus), running in lockstep with the Python golden model, so these are the cycles that actually happened, not a textbook drawing.

How to read a pipeline diagram: each row is an instruction, each column a clock cycle, and each cell the stage that instruction is in during that cycle. A starred cell means the instruction was held there (a stall). A struck-out row was fetched on the wrong path and flushed: it never wrote anything. The events row says what the control logic did in that cycle.

0 · The single-cycle core: one instruction per clock

Before the pipeline, the simple version: core_single.sv does fetch, decode, execute, memory and write-back all in one clock cycle. Every row below is one clock edge, and exactly one instruction finishes on each one. Watch three things: lw reads memory and writes the value into a register in the same cycle; beq writes no register, it only changes which PC comes next (taken: PC + offset, so the addi x4 at 0x14 never appears); and jal / jalr write the return address (PC + 4) into rd and jump.

addi x1, x0, 5
addi x2, x0, 5
sw   x1, 0x100(x0)
lw   x3, 0x100(x0)
beq  x1, x2, over
addi x4, x0, 99
over:
jal  x5, func
addi x6, x0, 7
beq  x0, x0, end
func:
addi x7, x0, 1
jalr x0, 0(x5)
end:

What to notice

  • pc jumps 0x10 → 0x18: the taken beq skipped 0x14.
  • jal x5 writes 0x1c (its own PC + 4) into x5. That is the return address.
  • jalr x0, 0(x5) jumps back to 0x1c and writes nothing (rd = x0).

Check yourself

Why is the single-cycle core's clock slow?

The clock period has to fit the longest path through everything in one cycle: instruction memory, then the register file, the ALU, data memory, and back to the register file. Every instruction pays for the slowest one (lw).

beq at 0x10 has offset +8. Where does it go, and why +8, not +2?

To 0x10 + 8 = 0x18. Offsets are in bytes, and instructions are 4 bytes, so +8 skips one instruction. (The encoding stores offset/2, because bit 0 is always 0.)

1 · The pipeline with nothing in the way

Five independent addis. Each instruction spends one cycle in each stage: IF (fetch), ID (decode + read registers), EX (ALU), MEM (data memory), WB (write the register). Once the pipe is full, one instruction finishes every cycle, even though each one takes 5 cycles start to finish. That's the whole point of pipelining: same latency, ~5× throughput.

addi x1, x0, 1
addi x2, x0, 2
addi x3, x0, 3
addi x4, x0, 4
addi x5, x0, 5

What to notice

  • Read a column top to bottom: in one cycle, five different instructions are in five different stages.
  • The diagonal staircase: instruction i enters IF at cycle i.

Check yourself

Latency vs throughput: what did pipelining change?

Latency (5 cycles per instruction) didn't improve; throughput did (1 instruction per cycle instead of 1 per 5 short cycles). Each stage is short, so the clock can be about 5x faster than the single-cycle one.

What sits between two stages, physically?

A pipeline register: a row of flip-flops (d_pc, d_instr, x_rs1_val ...) that captures everything the next stage needs at the clock edge.

2 · Data hazards and forwarding

addi x2, x1, 1 needs x1 one cycle after addi x1 computed it. The value won't be in the register file until WB, which is 2 cycles too late. Instead of waiting, the core forwards it: a mux in front of the ALU takes the value straight from the EX/MEM pipeline register (fwd = 1) or from MEM/WB (fwd = 2). No stall, no lost cycle.

addi x1, x0, 10
addi x2, x1, 1
add  x3, x1, x2
add  x4, x3, x3

What to notice

  • fwd_a / fwd_b in the event row say which ALU input got a forwarded value: 1 = from EX/MEM (the previous instruction), 2 = from MEM/WB (two back).
  • add x4, x3, x3 forwards x3 into both ALU inputs at once.
  • There are no bubbles: the staircase is as clean as the no-hazard case.
  • A detail you can find in the waveform: for addi x2, x1, 1 the unit also sets fwd_b = 1, because it compares the rs2 field, and for an I-type instruction those bits are part of the immediate (here 1 = x1). It's harmless, since the ALU's B input takes the immediate instead, and the events row leaves it out.

Check yourself

If the forwarding paths were missing, how many cycles would addi x2, x1, 1 wait?

Until addi x1 writes back. This core writes the register file in the first half (write-through to ID), so ID could read x1 when addi x1 is in WB: 2 stall cycles.

Both EX/MEM and MEM/WB hold a new value of the same register. Which one wins, and why?

EX/MEM, because it's the younger instruction, so its value is the newest. (tb test_forwarding_priority checks exactly this.)

3 · The load-use hazard: the one stall forwarding can't fix

A load gets its data at the end of MEM. The instruction right after it wants that data at the start of EX, which is the same moment, so no wire can deliver it in time. The hazard unit sees it in ID (the instruction in EX is a load whose rd matches rs1/rs2), stalls for one cycle (holds PC and IF/ID, sends a bubble into EX), then forwards from MEM/WB.

addi x1, x0, 42
sw   x1, 0x100(x0)
lw   x2, 0x100(x0)
addi x3, x2, 1
addi x4, x0, 0

What to notice

  • The stall cycle: addi x3, x2, 1 stays in ID for two cycles, and a bubble (·) goes into EX behind the lw.
  • Right after, fwd_a = 2: the loaded 42 goes from MEM/WB straight into the ALU.
  • sw x1 also got x1 forwarded (fwd_b = 1): stores need forwarding too, for the data being stored.

Check yourself

Why exactly one bubble and not two?

After one cycle the load is in WB and its data is in the MEM/WB register, so the normal MEM/WB forwarding path covers it.

How could a compiler avoid this stall?

Schedule an independent instruction between the load and its use (here: move addi x4 up). Same result, no bubble.

4 · Control hazards: taken branches flush

The core guesses "not taken" and keeps fetching the next instructions. The branch is resolved in EX. If it's taken, the two younger instructions already in IF and ID are on the wrong path: they're flushed (turned into bubbles) and fetch restarts at the target. Cost: 2 cycles per taken branch. A not-taken branch costs nothing.

addi x1, x0, 3
addi x2, x0, 3
beq  x1, x2, target
addi x3, x0, 111
addi x4, x0, 222
target:
addi x5, x0, 5
bne  x1, x2, target
addi x6, x0, 6

What to notice

  • When beq is in EX, the event row shows the redirect. The wrong-path addi x3 (111) gets through IF and ID, then is struck out and never reaches WB. addi x4 (222) was in IF during that same cycle, so it's dropped before ID and gets no row at all. That's the second lost slot.
  • bne x1, x2 is not taken: no flush, no lost cycles.
  • x3 and x4 are never written. Check the WB column.

Check yourself

Why is resolving the branch in EX worth 2 cycles, and how would you make it 1?

By EX, two younger instructions were already fetched (in IF and ID). Comparing in ID (an equality comparator next to the register file) would cost only 1, at the price of a longer ID stage and new forwarding paths into ID.

Why is flushing safe? Couldn't the wrong-path addi have changed something?

Nothing in IF or ID changes the architectural state: registers are written in WB and memory in MEM. So turning them into bubbles erases them completely.

5 · jal and jalr: calls and returns

jal x1, func is a call: it writes PC + 4 (the return address) into x1 and jumps. jalr x0, 0(x1) is a return: it jumps to x1 + 0 and writes nothing. Both are "always taken", so in this core they redirect from EX and flush 2 instructions, just like a taken branch.

jal  x1, func
addi x2, x0, 2
beq  x0, x0, end
func:
addi x3, x0, 3
jalr x0, 0(x1)
addi x4, x0, 44
end:

What to notice

  • Each jump flushes the two instructions behind it: the one in ID (struck-out row) and the one in IF (dropped, so it has no row). After the return, 0x04 runs again, which is why it appears twice.
  • jal writes x1 = 4 (the address of the instruction after it). The return lands there.
  • addi x4, x0, 44 after the jalr is fetched but flushed.

Check yourself

Why does jalr need the ALU but jal doesn't?

jal's target is PC + immediate, known from the instruction alone. jalr's target is rs1 + immediate (a register value), so it needs the register, possibly forwarded, and an adder.

jalr clears bit 0 of the target. Why?

The ISA says so (target = (rs1 + imm) & ~1), so the low bit can be used freely, e.g. for tagging. Instructions are 4-byte aligned anyway.
